# 需求分析：能力面全面单元化？（第 68 轮用户提出，瀑布第一步=分析非实现）

## 1. 用户的原始命题
「crates 下很多功能包，从架构上应该把功能迁移到 wasm-plugins，逐步实现全面的服务装配单元化。」

## 2. 第一性原理拆解：这句话里藏着三个不同的命题
| 命题 | 内容 | 现状 |
|---|---|---|
| P1 前端面单元化 | 一切 UI/面板=声明式服务单元 | **已完成**（D-212：13 卡+根直服+旧前端退役） |
| P2 能力实现单元化 | 能力的**实现**（现 host 内 Rust crate）改由可热插拔 WASM 组件承载 | 本提案对象 |
| P3 运行时自身单元化 | 把宿主/运行时也变成单元 | **原理上不可能**（承载者不能住进自己里——自举悖论） |

单元化的既定形态（产品里已有四类载体，无需发明新机制）：
**remote 端点**（13 卡+host-remote 桥）· **service 注册** · **tool 注册**（tool-loop 已双向桥接）· **loop**（echo/tool/llm-loop 已证可替换）。
所以 P2 的真问题不是"能不能"，是**每个能力值不值得换载体**。

## 3. 判定五问（逐 crate 过筛的标准）
1. **特权依赖**：需要 spawn 进程/sqlite 文件锁/墙钟 tick/裸网络栈？→ WASM 里做不了或必须开巨大 host-import 面 → 留 host
2. **热路径**：token 计数/diff 应用每轮都跑？→ 跨 wasm 边界税不值 → 留 host
3. **安全边界**：凭据、沙箱策略是裁决者——裁决者不能和被裁决者同层 → 留 host
4. **热插价值**：用户会「不重编热换/第三方扩展」这个能力吗？否 → 单元化是搬家不是架构
5. **import 面**：单元化后它需要向 host 要多少能力？超过 3-5 个新接口 = 假单元化（把耦合从编译期挪到运行时）

## 4. 逐 crate 初判（35 个，v1 待用户校正）
**地基·不可约（P3 排除项，8 个）**：dsh-cli(21.8k 启动器/serve/挂载)· dsh-wasmrt(5.6k 运行时本身)· dsh-core(7.7k 原语)· dsh-loader(5.3k 装配链)· dsh-schema(1.6k)· dsh-api(契约库)· dsh-brand · dsh-persistence(sqlite 事件日志权威——整个产品的地基本体)

## 4a. 地基 8 件套的第一性原理论证（第 68 轮用户追问，逐 crate 推导+自我推翻尝试）

**元命题**：单元化 = 「把*运行时实现*搬到接缝后面」。先问哪些东西在**定义上**不是
「可搬的运行时实现」，再问哪些是「可搬但不该搬」。得四根判据——

1. **时序论（自举根）**：承载者必先于被承载者存在。WASM 需要原生引擎才能跑；
   引擎的引擎无限回归。凡「在单元挂载*之前*就必须工作」的东西不可单元化。
2. **权威论（信任根）**：真相源与裁决者不可热换——换掉的瞬间，「历史/裁决是什么」
   的定义本身没了。真相源必须比任何插件更早存在、更晚消亡。
3. **范畴论（类型根）**：接口/词汇表不是它所定义系统的住户。字典不能被自己收录的
   词条搬家。契约 crate 是「单元如何存在」的语法，不是运行时实现。
4. **经济论（热路径税）**：技术上可搬，但每次调用交跨边界税且发生在启动序关键路上
   ——搬家成本 > 热插价值 = 伪架构收益。

| crate | 中几根 | 判定分级 | 未来可松动的边 |
|---|---|---|---|
| dsh-wasmrt | 时序 | **物理不可能**（wasm 里跑 wasmtime=无限回归/嵌套 Interpreter 崩塌） | 无。它已是「单元化能力的器官」，器官不能再是器官的房客 |
| dsh-cli | 时序（入口/监听/路由表/装配） | **不可约核 ≈ 启动+server+路由+装配**（估 2-3k）；其余=暂居核内的能力 handler | **可松动边①**：dispatch 臂持续外迁 service/remote 单元（host-remote 单载体模式已在这么干）——「可收缩内核」模式：核只收缩、不迁移、不消失 |
| dsh-loader | 时序（鸡生蛋：loader 加载单元，不能自己是被加载者） | bootstrap 脊柱不可能 | **可松动边②**：包源 resolver/远端 registry adapter 是「先有 loader 后有它」的下游位，日后可单元化（接缝形状=按源解析接口） |
| dsh-core | 范畴+时序（服务注册表=插槽语义本身；DI 容器 hosting 别人，不能被 host 于自己） | 不可能（实现层） | 数据形状可经 WIT 与单元共享；实现恒原生 |
| dsh-api | 范畴（RPC 消息模型/Remote 契约=单元的「语法」） | **范畴错位**（接口≠实现） | 无，也不该有 |
| dsh-brand | 范畴（跨边界共享 newtype） | 同上 | 无 |
| dsh-schema | 范畴一半（契约词汇）+ 经济（loader 启动依赖它+表单校验热路径） | **不可行非不可能**：可搬但税>值 | 若第三方要「自定义校验器」：开 validator 接缝，默认实现恒原生 |
| dsh-persistence | 权威（事件日志=产品真相源；boot 先于一切单元读它）+ 时序 + 技术（rusqlite 系 C，wasip1 工具链不可行） | **三重封锁**：热换 persistence=「历史是什么」的定义被热换 | 消费侧可单元化（备份/同步/导出 adapter 是用户），**存储本体恒 host** |

**结论（8/8 存活，但诚实分级）**：物理不可能 ×4 核（wasmrt/cli 入口/loader 脊柱/core
注册表）· 范畴错位 ×2（api/brand）· 不可行非不可能 ×1（schema）· 权威根 ×1
（persistence）。**边界是承重墙不是水泥墙**：两处可松动边（cli 内核只收缩、
loader 下游 resolver 可单元化）已标出——即使这样，「8 件套作为 crate 形态永不
整体单元化」的终态判定成立。

**反向自检（本应动摇结论却未动摇的尝试）**：①「把 loader 用两阶段自举（微型原生
loader 先起，主 loader 即第一单元）」——败于时序论：主 loader 若可热换，产品装配
语义的可信基就没了，等价于把 persistence 换掉；②「schema 校验经单元做」——败于
经济论+启动序（boot 校验发生在任何单元挂载之前）；③「persistence 换 KV 后端
就 wasm 化了」——后端可换 ≠ 真相源可热插，authority 与 encoding 是两回事。

## 5. 常见错误（本分析主动堵死）
**把「全部单元化」执行成「全部塞进 WASM」**：地基不可自举、特权出不了沙箱、热路径交税、裁决者不能下场——强行全迁会得到一个更慢、更安全面更大、更难测的系统。「全面」的正确定义=**一切能力都「可」经单元接缝提供**（接缝全覆盖），而非一切实现都在 wasm 里。
