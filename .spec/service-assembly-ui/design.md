## 1. 架构模型（一条主线，一问三答）

### 1.1 主线（数据流）

```
┌─ Rust 插件侧（wasm 组件）─────────────────────────────┐
│  静态：plugin.xml（构建期 & /plugins/<name>/** 分发）      │
│    或  动态：describe-UI RPC（运行期组 XML 返回）          │
│  —— 产「UI 声明（数据）」，产物是 XML/JSON 文本，不是代码    │
└───────────────┬────────────────────────────────────────┘
                │ 数据（XML/JSON）
                ▼
┌─ 浏览器 GUI 壳 ────────────────────────────────────────┐
│  通用渲染器（单一 React 组件，只读声明）                    │
│    ├─ 解释数据 → 映射 React 元素 + 施加样式               │
│    └─ 动作按钮 → 宿主 RPC → wasm 插件 host-api 回调       │
└─────────────────────────────────────────────────────────┘
```

要点一：**声明是数据，不是代码**。「通用渲染器」= 一段写一次、跑在浏览器的代码，所有插件共享；
它读 XML/JSON 数据就渲染，无需为每个插件「生成」任何前端代码。

要点二：**渲染器必须在浏览器（前端）实现**。交互（按钮/输入/状态/动态数据）必须由浏览器内的
代码直接响应 DOM 事件；Rust 到不了 layout/paint，也不能当交互渲染器。「交互需浏览器端代码」
是第一性约束，不是可选。

要点三：**Rust 的角色 = 生声明 / 数据面 / 权限 / 动作执行**，独独不做渲染（见 §2 矩阵）。

### 1.2 可选加速支线：SSR 首帧

```
Rust 宿主把 声明(XML) + 初始数据 快速拼成 HTML 字符串 → 先发给浏览器（首屏更早可见）
→ 前端渲染器随后接管交互（hydrate 续接）
```

- **定位：可选加餐，非核心闭环验收项**。本设计不把它列为验收硬项。
- 理由：「渲染」拆两半——前半（XML→HTML 字符串）Rust 能做且快，换「首帧更早」；后半
  （layout/paint + 事件 + 交互）是浏览器引擎的事，Rust 够不着，谁也不省。
- 实现前提（后续才评估）：Rust 侧得有「声明→HTML 字符串」的模板拼装器；前端渲染器要支持
  对 SSR 首帧的接管（hydrate 语义）。不满足则可只走纯客户端渲染，架构不塌。

## 2. 组件职责矩阵

| 组件 | 归属端 | 职责 | 说明 / 约束 |
|---|---|---|---|
| UI 声明生产者 | Rust 插件（wasm） | 静态 `plugin.xml` 或动态 `describe-UI` 组 XML | 产物 = 数据文本；不进「代码」通道 |
| 静态分发 | Rust 宿主（web.rs） | `/plugins/<name>/<rest>` 静态挂接（含 `.xml`/`.json`/资源） | 复用既有 `serve_package_asset` 机制（D-175） |
| 数据面 / 权限 | Rust 插件（wasm） | 鉴权、取数、动作按钮回传后的真实执行 | host-api 回调；RPC 动作白名单受宿主校验 |
| SSR 首帧（可选） | Rust 宿主 | XML+初始数据 → HTML 字符串 | 可选加速；非验收项；不实现可纯客户端渲染 |
| 通用渲染器 | 浏览器 GUI 壳（前端） | 读声明数据 → React 元素 + 样式 + 事件 + 动作 RPC | 单一组件；只读数据 → 天然沙箱（无插件 JS 进浏览器） |
| 发现/清单 | 前端 + 宿主 | 从既有 `pluginInventory` 数据面 / `/plugins/<name>/**` 读清单，免重启随 refresh 更新 | 对齐既有发现面（D-175/D-177） |

## 3. 概念纠偏（本设计的智力资产——防再次走回三条弯路）

1. **「XML → 翻译成 TS/CSS → 交给浏览器」是错的，而且有害**。
   - 浏览器不执行 `.ts`（TS 是人写的、要编译成 JS 的语言）；即便真走 codegen，产物也是 JS。
   - 一旦「翻译产物」是可执行代码，就回到 P1 的风险（浏览器跑插件作者的代码 → 沙箱没了）。
     P2 的立身之本就是「渲染器只读数据，无任意 JS 执行」。声明是数据，不需要变成代码——
     浏览器渲染任何东西都是「声明(数据) + 引擎(代码)」并存，引擎（渲染器）能读就够了。

2. **「通用渲染器放 Rust、由 Rust 渲染更快」是错的**。
   - 把「渲染」拆两半：前半（声明→HTML 字符串）Rust 能做 = SSR 首帧加速（§1.2 可选）；
     后半（layout/paint + 事件 + 交互）是浏览器引擎的领域，Rust/wasm 进不了，谁也绕不开。
   - 交互（按钮/输入/动态）迫使渲染器必须在浏览器里：服务端渲染每次交互都是一整轮回传
     （表单刷新模型），延迟高、状态乱、体验差。
   - 所以「SSR 提速」的合法位置是**首帧加速**（可选），不是替代客户端渲染。

3. **「声明不需要被翻译，只需被解释」**：正确链条是「XML/JSON 数据 → 前端通用渲染器（一段
   写一次的代码）→ DOM + 动作 RPC」。渲染器一次实现、无限内容 = 「通用」的含义。

## 4. 边界（本轮明确不做）

- **不含声明 schema 字段草案**（元素/布局/绑定/动作的具体字段集）——试点选定后单独设计；
  schema 对齐 MCP Apps / A2UI / Adaptive Cards 的 JSON schema 子集方向（不发明私有 DSL）。
- **不实现 SSR 首帧**——本设计只落定「可选」定位；是否做、怎么做留后续评估。
- **不写任何实现代码**（延续用户「只确认方向 / 讨论方案」的阶段边界；编码在相邻轮次决议后）。
- 不推翻 P2 方向与既有需求边界（requirements.md §4）。
